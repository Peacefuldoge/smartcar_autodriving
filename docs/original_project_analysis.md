# 原项目分析

## 1. 项目本质

这不是单纯的“摄像头循迹小车”，而是一套已经形成闭环的智能车系统：

1. **人工驾驶数据采集**：手柄控制车辆，摄像头同步保存图像，记录转向值作为监督标签；
2. **车道循迹模型**：摄像头画面经 HSV 二值化后输入 Paddle Lite 回归模型，输出连续转向量；
3. **目标检测模型**：同一帧图像同时输入 256×256 Tiny-YOLO，用于识别赛道事件/标志；
4. **行为规则层**：根据连续多帧检测结果执行超车、限速、停车、左转等动作；
5. **车辆通信层**：Python 通过 `libart_driver.so` 把油门/转向发送到串口；
6. **下位机层**：MCU 将“转向差值”转换成左右轮差速 PWM。

因此从工程结构上，它已经对应现代自动驾驶/机器人系统常见的 **Perception → Decision → Control** 三层架构，只是当时所有层被写进了少数几个比赛脚本里。

## 2. 原始文件中最重要的主线

### `Auto_Driver_client2.py`

这是自动驾驶主循环的核心版本。每帧同时执行两条视觉支路：

- HSV 黄色区域 → 128×128 → Paddle Lite → 转向回归；
- RGB → 256×256 → Paddle Mobile Tiny-YOLO → 目标框/类别/置信度。

随后将模型转向结果通过一套分段经验标定转换成实际舵机值，并把检测结果交给 `user4.user_cmd()`。

### `user4.py`

这是最终赛道规则层。根据代码中的实际分支，可以还原出如下类别逻辑：

| ID | 代码行为 |
|---:|---|
| 0 | 超车动作 |
| 1 | 停车线/一次性停车流程 |
| 2 | 进入限速状态 |
| 3 | 解除限速 |
| 4 | 左转偏置 |
| 5 | 锥桶右转事件（原代码只有计数，动作未完成） |
| 6 | 锥桶左转事件（原代码只有计数，动作未完成） |
| 7 | 锥桶右转中段事件（原代码只有计数） |
| 8 | 锥桶左转中段事件（原代码只有计数） |
| 9 | 斑马线停车 |
| 10 | 停车/入库结束事件 |

注意：`user4.py` 顶部旧注释中的 `0 red / 1 green ...` 已经与实际代码不一致，说明它是从更早版本复制过来的残留注释，不能再作为标签定义依据。

### `Data_Coll4.py`

负责训练数据采集：

- `/dev/input/js0` 读取 Linux joystick；
- `/dev/video2` 读取摄像头；
- `/dev/ttyUSB0` 控制车辆；
- 多进程分别完成控制、图像保存和转向标签保存；
- 最后把 TXT 转成 NPY。

这个思路是对的，但实现上同步关系较脆弱，所以整理版改为“图片文件名 + CSV 同一行标签”的显式数据对齐。

### `sketch_oct31a.ino`

下位机通过 `Serial3 @ 38400` 接收上位机命令，把：

```text
throttle - 1500
steering - 1500
```

转换成：

```text
left  = throttle_delta - 0.2 * steering_delta
right = throttle_delta + 0.2 * steering_delta
```

然后限制到 ±100 并输出 PWM，因此本质上是一个简单的差速混控器。

## 3. 模型与图像处理

### 循迹模型

原始流程只保留 HSV 中 `[25, 75, 190] ~ [40, 255, 255]` 的区域，明显是在追踪黄色道路标线。它不是传统 PID/几何循迹，而是把处理后的视觉图直接交给神经网络回归转向量。

模型输出并没有直接作为舵机值，而是先：

```text
servo = output * 600 + 1200
```

再经过非线性的人工分段修正。这说明当时很可能通过实车实验补偿了舵机死区、左右响应不对称或模型输出分布的问题。

### 目标检测

检测模型使用 Paddle Mobile FPGA 推理，输入为 256×256 RGB，标准化方式为：

```text
x = (x - 127.5) * 0.007843
```

输出每行包含：

```text
[label, score, xmin, ymin, xmax, ymax]
```

这部分接口整体是完整的，但原主程序里混入了大量训练配置（epoch、SGD、augmentation 等），实际上推理阶段根本不需要。

## 4. 原代码中的主要工程问题

### 4.1 多版本复制，而不是模块化

`Auto_Driver_client2.py`、`client3.py`、`follow.py`、`Auto_Data_Coll_Client.py` 的相似度非常高，主要区别只是：

- 引用了不同 `user*.py`；
- 舵机标定参数不同；
- 某些版本关闭了循迹，固定转角 1500。

这说明当时是通过复制整个文件来做实验分支。比赛阶段很常见，但 GitHub 上会让读者很难判断哪个才是主线。

### 4.2 状态变量 bug

`user4.py` 中存在：

- `used` 被读取但从未定义；
- `pre_vle` 拼写错误；
- `limited=True` 后，后面的 `slow == False` 又把速度强制改成 1600，导致限速可能失效；
- 所有类别共用一个全局 `number` 计数器，A 类目标刚累计的帧数可能被 B 类目标继续使用。

这些都已经在重构版中改成显式状态和“每类别独立计数器”。

### 4.3 一个检测结果可能重复下发很多次控制命令

原行为层大量使用：

```python
if label == X:
    ...
else:
    lib.send_cmd(...)

if label == Y:
    ...
else:
    lib.send_cmd(...)
```

因此对一个目标执行一次 `for` 循环时，后续多个 `else` 都可能重复调用 `send_cmd`。这会让实际控制频率和优先级很难推断。

重构后每帧先得到一个 `BehaviorDecision`，再统一下发一次；需要超车这类动作时，使用显式 `TimedCommand` 序列。

### 4.4 推理循环存在重 I/O 调试代码

原 `predict()` 每帧会尝试把浮点 Tensor 当编码图像 `imdecode`，并写 `zzzzz_test.jpg`。这不但逻辑不成立，还会显著拖慢实时循环和损伤存储介质。

整理版已删除所有此类每帧落盘调试代码。

### 4.5 循迹 Tensor 布局存在历史兼容问题

原代码构造的是 `(1, H, W, C)`，但随后直接：

```python
reshape(1, 3, 128, 128)
```

没有做标准的 HWC→CHW `transpose`。从现代深度学习习惯来看这非常可疑，但如果当年模型训练和部署都使用同样的数据排列，直接“修正”反而可能让模型完全失效。

因此整理版没有偷偷改掉，而是把它做成：

```json
"legacy_memory_layout": true
```

明确告诉后续维护者：这是需要通过实车/模型重新验证后才能修改的兼容项。

### 4.6 下位机安全性不足

原 firmware 中“串口长时间无数据自动停车”的代码被注释掉了；如果上位机崩溃，小车可能继续执行最后一次速度命令。

整理版加入了 300 ms command watchdog：超过时间没有收到完整命令时输出 0 PWM。

此外原协议使用：

```text
low + high * 255
```

而通常 16 bit 小端应该是 `*256`。由于压缩包里缺少 `libart_driver.so` 的发送端实现，无法证明它是 bug，所以整理版**保留 255**并在代码中明确标注，避免擅自破坏协议兼容性。

## 5. 哪些文件可以确定是不必要的

- `__pycache__`：Python 自动生成；
- `.vscode/settings.json`：个人 IDE 配置；
- `Image.py`：Pillow 库源码副本，不属于项目；
- `number_judge.py`：只有 import，没有功能；
- `imghsv = ...py`：明显是临时粘贴残片；
- `import codecs.py`：不完整、包含语法错误的检测测试脚本；
- `hsv.py`、`read_npy.py`、`rename.py`、`sort.py`、`re.py`：全部带本机 Windows 绝对路径的一次性脚本；
- `re.py` 还会与 Python 标准库 `re` 同名，存在模块遮蔽风险；
- `resnet.py`：虽然代码本身有价值，但没有被任何主线文件 import，与当前车辆运行链路无关；
- 多个 `Auto_Driver*` / `user*` 旧分支：应由 Git 历史管理，而不是一起堆在主目录。

## 6. 现在这个 GitHub 版最适合怎么描述

从项目能力来看，比较准确的定位是：

> 基于嵌入式视觉与深度学习的智能车系统，融合车道循迹回归、Tiny-YOLO 目标检测、规则状态机决策与下位机差速控制，并配套手柄驾驶的数据采集流程。

它比单写“自动驾驶车模”更能体现你当时实际做过的工作：不仅有模型，还有数据闭环、设备通信、控制逻辑和嵌入式执行。
